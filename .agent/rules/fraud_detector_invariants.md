# Fraud Spike Detector Architectural Invariants & Rules

## 1. Core Principles
- **Explainability is Mandatory**: Every alert generated by the system must include a human-readable audit record detailing the top contributing features, threshold comparisons, and plain-language reasoning. No black-box decisions.
- **Strictly Defense-Only**: No code path may simulate, assist, or double as an attack or exploitation tool.
- **Opt-in Consent Layer**: Cross-merchant data sharing is strictly opt-in and defaults to `False`. A merchant's fraud detection must never be gated or disabled based on their consent choice.
- **Honest Time-Based Evaluation**: Offline evaluation must always use a time-based train/test split to prevent lookahead bias. Report precision, recall, false-positive rate, and estimated false-positive dollar costs transparently.
- **Idempotency**: Alert generation must be idempotent, keyed by `(merchant_id, window_start, window_end)` to prevent duplicate alerts upon replay or retries.
- **Graceful Error Handling**: Malformed transaction payloads must be logged and routed to a dead-letter record rather than crashing the ingestion pipeline.
